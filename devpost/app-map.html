User Story & Acceptance Criteria Assistant

Project goal: turn a rough business requirement into a backlog-ready story, clear Gherkin acceptance criteria, and dependency/open-question output.

Code route

1. Intake

app.py defines the Streamlit form and optional role selector.

  • ROLES
  • st.text_area(...)
  • st.selectbox(...)

2. Prompt construction

build_prompt(raw_request, role) transforms the input into a strict agile-analysis prompt.

  • Story format: Como [rol], quiero [acción], para [beneficio]
  • Gherkin acceptance criteria
  • Technical dependencies and open questions

3. Generation and fallback

generate_story_result(raw_request, role) checks validation, then calls Gemini or falls back safely.

  • build_demo_fallback(...) for no API key
  • generate_content_with_model_fallback(...) for model retry logic
  • build_response_from_model(...) normalizes output

4. Output formatting

build_markdown_output(result) turns the result into copy-ready Markdown.

  • Historia de usuario
  • Criterios de aceptación
  • Dependencias técnicas
  • Preguntas abiertas

5. UI rendering

render_story_result(result) shows the request, output card, and copy/download controls.

  • Download as Markdown
  • Buttons for copy-to-clipboard
  • Validation and error states

Key files

  • app.py — complete app logic and UI
  • requirements.txt — Streamlit + dotenv + Gemini SDK
  • devpost/checklist.md — build status and final review record
  • devpost/spec.md — technical product specification

Reusable practice

Use one realistic business sentence as a test harness before anything else:

"Solo los administradores pueden descargar reportes de ventas"

Then verify the app produces three things in a single pass:

  1. a user story in the expected format,
  2. at least one Gherkin scenario, and
  3. a dependency/open-question section that flags ambiguity.

This keeps the kernel honest and prevents the app from drifting into generic AI writing without business discipline.
